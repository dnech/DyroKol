# Архитектура

Документ для тех, кто хочет понять устройство DyroKol или менять код. Пользовательские понятия
описаны в [Концепциях](concepts.md).

## Обзор

```
                    ┌──────────────────────── relay (dyrokol server) ───────────────────────┐
 посетитель ──TCP──▶│ relay-порты ─┐                                                         │
                    │              ├─▶ route cache ─▶ executeEgress ─┬─▶ egress.Dial (local) │
 агент ─TLS 1.3─────▶ handshake ─▶ Session ── yamux ─▶ streams ──────┘   или dial-стрим      │
                    │                  │  push (конфиг) ◀── Store (2 зашифрованные SQLite)   │
                    │                  │  report ──▶ статистика ──▶ flush каждые 5 с         │
                    │ admin HTTP (в памяти) ◀── admin-стрим от admin-агента                  │
                    └─────────────────────────────────────────────────────────────────────────┘
```

Один бинарник, три слоя:

1. **Транспорт**: TLS 1.3 + [yamux](https://github.com/hashicorp/yamux) — много независимых
   потоков поверх одного TCP-соединения агента.
2. **Плоскость управления**: рукопожатие, push конфигурации, отчёты о трафике, админ-API.
3. **Плоскость данных**: пересылка байтов между посетителем и целью.

## Карта пакетов

| Пакет | Ответственность |
| --- | --- |
| `cmd/dyrokol` | CLI: разбор флагов, конфиги, запуск `server`/`client`, управление службой Windows (`service_windows.go`). |
| `internal/server` | Relay: рукопожатие, сессии, relay-порты, push, статистика, админ-API и встроенный UI. |
| `internal/agent` | Агент: сессии с relay, открытие входных портов, выполнение выходных точек, отчёты, локальная админка. |
| `internal/store` | Хранилище: зашифрованные базы, сущности, транзакции, бэкап. |
| `internal/protocol` | Формат сообщений и кадров, рукопожатие, токены. |
| `internal/transport` | TLS-сертификат, pinning/TOFU, настройки yamux, тюнинг сокетов. |
| `internal/traffic` | Учёт трафика: счётчики, адреса посетителей, живые соединения, `Port.Relay`. |
| `internal/copyio` | Пересылка байтов с пулом буферов, двунаправленный `Pipe`. |
| `internal/egress` | Выполнение выходной точки: direct или встроенный SOCKS5-сервер, с проверкой фильтра назначения. |
| `internal/socks5` | Минимальный SOCKS5-клиент и сервер для SOCKS5-выхода (RFC 1928/1929, только CONNECT). |
| `internal/filter` | Разбор и применение списков allow/deny. |
| `internal/config` | Каталог данных и приоритет «флаг → переменная → значение по умолчанию». |

Зависимости направлены вниз: `server` и `agent` используют `protocol`, `transport`, `traffic`,
`egress`, `filter`; `store` знает только `filter` и `protocol`; листовые пакеты друг от друга
почти не зависят.

## Протокол

После TLS-рукопожатия обмен идёт **кадрами**: 4 байта длины (big-endian) + JSON, максимум 1 МиБ.

### Рукопожатие

Агент отправляет `Hello`, relay отвечает `Reply` (оба — кадры, таймаут 15 секунд):

```jsonc
// агент → relay
{ "version": 4, "purpose": "connect",       // или "init"
  "token": "cl_…", "db_password": "…",       // purpose=connect
  "admin_token": "adm_…",                    // purpose=init
  "agent_version": "1.0.0" }

// relay → агент
{ "role": "admin", "version": "1.0.0", "admin_token": "api_…" }     // успех
{ "error": { "code": "unauthorized", "message": "unknown token" } } // отказ
```

- `connect` — обычное подключение. Если база заблокирована, relay открывает её паролем из Hello.
- `init` — регистрация первой машины: relay создаёт обе базы, машина с токеном `admin_token`
  становится admin. После ответа relay закрывает это соединение, а агент подключается заново
  уже как `connect`.
- Коды ошибок: `locked`, `unauthorized`, `db_exists`, `bad_init`, `version`, `internal`.
- `admin_token` в ответе приходит только admin-машине и только если relay знает его открытым. Сгенерированный токен хранится в `meta` базы конфигурации (зашифрован вместе с ней), а не в файле.
- Версия протокола должна совпадать точно.

### Потоки yamux

После успешного рукопожатия поверх соединения стартует yamux (relay — сервер, агент — клиент,
keep-alive 10 с, окно потока 2 МиБ). **Первый кадр каждого потока** — `StreamHeader` с типом:

| Тип | Направление | Содержимое после заголовка |
| --- | --- | --- |
| `report` | агент → relay | Серия кадров `Report` каждые 2,5 с: `stats` (дельты и число активных соединений по портам), `peers` (дельты по адресам), `live` (открытые соединения). Один писатель на поток. |
| `push` | relay → агент | Кадр `ConfigPush`, в ответ кадр `ConfigAck` (таймаут 15 с). |
| `dial` | relay → агент | В заголовке `EgressSpec`; дальше сырые байты — агент подключается к цели и пересылает данные. |
| `route` | агент → relay | В заголовке `inport_id`; дальше сырые байты. Relay находит маршрут, исполняет выход и пересылает данные. |
| `admin` | агент → relay | Сырые байты: relay передаёт стрим своему admin HTTP-серверу через слушатель в памяти (порт не открывается). Только для роли `admin`. |

### Конфигурация (`ConfigPush`)

```jsonc
{ "version": 12,
  "in":  [ { "inport_id": 3, "port": 8080, "label": "web",
             "allow": [], "deny": ["10.0.0.0/8"],
             "egress": { "machine": "relay|<hash>", "type": "direct", "host": "…", "port": 5000, … } } ],
  "out": [ { "endpoint_id": 2, "type": "direct", "target": "127.0.0.1:5000", "from": ["relay"] } ] }
```

`in` — порты, которые агент должен открыть (только с маршрутом). `out` — справочно, для лога агента.
Push — это **полное состояние** для машины, а не разница: агент приводит свои listener'ы
к описанному (закрывает лишние, открывает недостающие, обновляет конфиг существующих).

`ConfigAck` содержит `error` (весь push отклонён: неверный порт, дубликат, кривой фильтр) либо
`bind_errors` (часть портов не открылась, остальное применено).

## Жизненный цикл relay

1. `Run`: загрузка/создание сертификата, туннельный listener. **База заблокирована**,
   `store == nil`; админки и relay-портов нет.
2. Первое успешное `connect` с паролем (или `init`) → `activateLocked`: сохраняет store, сбрасывает
   кэш маршрутов, открывает relay-порты, запускает админ-HTTP и два фоновых воркера
   (`flush` каждые 5 с, `repush` каждые 15 с).
3. Каждая сессия: `register` → push конфигурации → цикл `Accept` потоков → `unregister`.
   Новая сессия машины вытесняет старую.
4. Остановка (`Close`): закрытие listener'ов и сессий, ожидание воркеров, **финальный flush**,
   запечатывание баз.

### Поток изменения конфигурации

```
API-хендлер ─▶ store.mutate: транзакция + config_version++ + seal на диск
            ─▶ server.configChanged: сброс кэша маршрутов
                                     синхронизация relay-listener'ов с базой
                                     broadcastConfig → pushConfig каждой сессии
```

`pushConfig` сериализован на сессию (`pushMu`) и пропускает машину, уже применившую текущую
версию. Если ack содержал ошибки bind или связь оборвалась, `repush` пробует снова — раз в 15 секунд.

### Кэш маршрутов

Принятие соединения не должно ходить в базу. `routeCache` хранит разрешённый маршрут порта
(порт, выходная точка, скомпилированный фильтр) и сбрасывается при любом изменении. Чтобы
загрузка, начавшаяся до сброса, не вернула устаревшее значение, у кэша есть **счётчик поколений**.
Загрузка записывается, только если поколение не изменилось.

## Агент

- `runServer` держит сессию с каждым relay: пауза между попытками растёт 1 → 15 с, сбрасывается
  после 30 с стабильной работы.
- Порты хранятся по ключу **(relay, id порта)**: идентификаторы уникальны только в пределах relay,
  а один номер порта на хосте — только один (конфликт отдаётся как bind error).
- Для порта с выходной точкой на той же машине трафик не идёт через relay (`Egress.Machine ==` наш
  `key_hash`); иначе открывается `route`-стрим.
- Каждый порт — это `traffic.Port` (счётчики + живые соединения) и набор адресов посетителей;
  отчёт каждые 2,5 с **сбрасывает** накопленные дельты, поэтому ничего не теряется и не
  дублируется.
- Закрытие порта закрывает и его соединения (`ConnSet.Shut`).

## Хранилище

Две независимые базы, каждая — **SQLite в памяти**, запечатанная на диск целиком
(`sealed.go`):

```
файл:  "DYRK1" | salt(16) | nonce(12) | AES-256-GCM( сериализованная SQLite-база )
ключ:  scrypt(пароль, salt, N=2¹⁵, r=8, p=1) → 32 байта
```

Драйвер `modernc.org/sqlite` умеет `Serialize`/`Deserialize` образа базы, поэтому открытый текст на
диск не попадает вообще. Сохранение — шифрование образа новым nonce и атомарная замена файла
(`.tmp` → `rename` с `fsync`). На базу приходится одно выделенное соединение.

| База | Содержимое | Когда записывается |
| --- | --- | --- |
| **config** (`*.db.enc`) | машины, входные порты, выходные точки, маршруты, настройки, версия конфигурации | при каждом изменении конфигурации |
| **data** (`*.data.db.enc`) | итоги, минутные точки, адреса посетителей, присутствие машин, журнал | при `flush`: каждые 5 с, пока есть трафик или онлайн-машины (присутствие тоже записывается) |

Деление нужно, чтобы частые записи статистики не перешифровывали конфигурацию, а потеря
data-базы была безопасной.

Правила работы с базой:

- Любое изменение конфигурации — **одна транзакция**, внутри неё же растёт `config_version`
  (`store.mutate`), затем запечатывание. Операция либо целиком применена, либо нет.
- Один агрегирующий снимок: `Topology()` читает все четыре таблицы под одной блокировкой, поэтому
  ответы статуса и конфигурации агентам согласованы.
- Ограничения целостности — в схеме: `UNIQUE(machine, port)` для входных портов,
  `UNIQUE(machine, type, host, port, socks5_host, socks5_port)` для точек, `UNIQUE(inport_id)` для
  маршрутов, внешние ключи с каскадным удалением маршрутов.
- У маршрута есть флаг `enabled` (схема 3; база схемы 2 мигрирует при открытии). Выключенный маршрут не резолвится (`Resolve` не возвращает точку), не попадает в конфигурацию агентам и в списки «кто сюда ходит»; бэкап хранит флаг, а бэкап без него восстанавливается как включённый.
- Маршруты: у входного порта не больше одного (`UNIQUE(inport_id)`), в одну выходную точку их может
  вести сколько угодно. `SetEndpointRoutes` атомарно задаёт весь набор входных портов точки
  (переносит порты с других точек, снимает лишние) и возвращает порты, потерявшие прежний маршрут;
  вызов без изменений не тратит версию конфигурации.
- Раскладка схемы маршрутов (`MapLayout`: позиции портов и подписи/рамки) лежит в `meta` config-базы
  одним JSON-значением. Она общая для всех администраторов, входит в бэкап (ключи узлов
  `in:<id>`/`eg:<id>` переназначаются при восстановлении, так как идентификаторы создаются заново) и
  **не** увеличивает версию конфигурации: агентам она не нужна.
- Изменение номера входного порта (`UpdateInPort`) и цели выходной точки (`UpdateEndpoint`) — обычные
  транзакции с проверкой уникальности; `UpdateRoute` перенаправляет один маршрут атомарно.
- Удаление сущности чистит и её runtime-данные (`dropRuntimeLocked`).
- Версия схемы хранится в `meta`; совместимости со старыми схемами нет (при несовпадении —
  ошибка), кроме одного встроенного шага 2 → 3 (добавляет `routes.enabled`).
- Ошибки хранилища типизированы (`Error{Kind, Msg}`: `ErrInvalid`, `ErrNotFound`, `ErrConflict`),
  HTTP-слой переводит их в статусы 400/404/409 в одном месте.

## Учёт трафика

`traffic.Port` объединяет `Counters` (атомарные байты, соединения, активные), `ConnSet`
(живые соединения; `Shut` закрывает их и блокирует новые) и метод `Relay`, который пересылает байты
через `copyio.Pipe` и начисляет трафик на порт и на адрес посетителя.

- `Counters.Drain` возвращает дельты с прошлого вызова и текущее значение gauge.
- На relay дельты relay-портов и принятые отчёты агентов копятся в памяти и сбрасываются в data-базу
  в `flush`. Отчёты агентов принимаются только по портам этой машины.
- Итоги (`totals`) суммируются в базе; график строится по минутным точкам, итог живёт долго.

## Админ-API и UI

- `adminHandler` создаётся один раз при разблокировке и получает готовый `*store.Store`, поэтому
  хендлерам не нужны проверки «база заблокирована».
- Все эндпоинты проходят через `guard`: токен, проверка `Origin`.
- Статус (`/api/status`) собирается из одного `Topology()` плюс runtime-срез сервера.
- UI — статические файлы, встроенные в бинарник (`go:embed web`).

### Устройство UI

Без сборки: нативные ES-модули и import map, Preact + htm лежат в `web/vendor/`.

```
js/main.js          точка входа: логин или оболочка, диалоги, тосты
js/shell.js         каркас: боковое меню, верхняя панель, роутер, тема
js/state.js         состояние приложения: токен, снимок статуса (опрос 5 с), mutate/useAction
js/lib/             api (клиент API), store (наблюдаемые хранилища, usePolled),
                    router (хеш-роутер), format, html (Preact+htm)
js/ui/              кит: кнопки, поля, статусы, таблицы-обёртки, меню, диалоги (на промисах),
                    тосты, редактор фильтров, иконки
js/pages/           страницы: overview, machines, ingress, egress, activity, logs, settings, login
js/charts/          график трафика (SVG) и схема маршрутов routemap.js (узлы и аннотации — HTML, линии — SVG)
css/app.css         токены (тёмная/светлая темы), раскладка и компоненты
```

Принципы:

- Состояние приложения — один наблюдаемый store; страницы читают его хуком `useApp()` и меняют
  только через `mutate`/`useAction`, которые обновляют снимок и показывают результат.
- Страницы Activity и Logs опрашивают свои эндпоинты сами (`usePolled`); опрос ставится на паузу в
  фоновой вкладке.
- Диалоги — промисы: `openDialog(render)` возвращает результат закрытия, `confirmDialog` —
  `true/false`.
- Выпадающие меню позиционируются по координатам окна, чтобы их не обрезали таблицы.
- Схема маршрутов (`charts/routemap.js`) строится из того же снимка статуса и общей раскладки
  (`lib/maplayout.js`: загрузка при открытии страницы, сохранение с задержкой 0,5 с). Это свободный
  холст: порты и аннотации позиционируются абсолютно и перетаскиваются pointer-событиями (мышь,
  перо, палец), шаг сетки 10 пикселей. Слои снизу вверх: рамки, подписи, линии (SVG), порты. Порты,
  которым место не назначено, встают колонками (входные слева, выходные справа) под уже
  расставленными; при первом перетаскивании фиксируются позиции **всех** портов, чтобы добавление
  новых не сдвигало остальные. Линии выходят из той стороны порта, что обращена к цели. Состояние
  порта всегда подписано текстом, а не только цветом.
- Схема смотрится через окно просмотра с трансформацией (`translate` + `scale` у «мира»): панорама
  перетаскиванием фона, масштаб кнопками, Ctrl + колесом, щипком, подгонка Fit. Перетаскивание
  портов и аннотаций переводит экранные пиксели в координаты схемы делением на масштаб. Полноэкранный
  режим — это слой `position: fixed` (z-index ниже диалогов) плюс Fullscreen API на документе, поэтому
  диалоги работают и в нём. Позиции портов по умолчанию не зависят от размера окна, иначе раскрытие
  на весь экран сдвигало бы нерасставленные порты. Вид (панорама, масштаб) не сохраняется.
- Страница Routes — таблица «одна строка — один маршрут» (`pages/routes.js`): ячейки правятся на
  месте через `PATCH /api/routes/{id}`, последняя строка создаёт маршрут.
- Цвета статусов фиксированы и всегда сопровождаются текстом; график использует палитру,
  проверенную на различимость для дальтоников в обеих темах.

## Инварианты, которые нельзя ломать

1. **На диске нет открытого текста.** Базы живут в памяти, на диск — только `sealed`-образ.
2. **Любое изменение конфигурации идёт через `store.mutate`** (транзакция, версия, сохранение),
   а после него вызывается `server.configChanged()`.
3. **Агент не определяет маршрут:** relay проверяет принадлежность порта и сам выбирает выход.
4. **Порядок блокировок: `Server.mu` → `Store.mu`**, но не наоборот (store ничего не знает о
   сервере). Обращение к кэшу маршрутов (он ходит в store) не делается под `Server.mu`.
5. **Фильтры работают как fail closed:** нераспознанный фильтр блокирует трафик.
6. **Версия протокола и схемы** повышаются при несовместимых изменениях (`protocol.Version`,
   `store.schemaVersion`); миграций нет, кроме 2 → 3.
7. **Идентификаторы входных портов уникальны только в пределах relay**, номера портов — только в
   пределах машины. Нельзя ключевать состояние только по номеру порта или ID.
